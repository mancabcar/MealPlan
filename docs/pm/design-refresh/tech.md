# Rediseño visual moderno de Comidas: Technical design
_Status: Draft · Updated: 2026-09-22_
_Related: [spec](spec.md) · [brief](brief.md)_

## Summary
This is a pure visual re-skin: no data model, API, or store changes. The recommended approach is (1) a dark-only token system built with Tailwind v4's `@theme` (extending the pattern already used for `--color-background`/`--color-foreground`), (2) Space Grotesk + Manrope self-hosted via `next/font/google` exactly like the existing Geist setup, (3) `lucide-react` for the stroke-icon set instead of hand-rolled SVGs, and (4) a small new `src/components/ui/` primitives layer (Card, Chip, ProgressRing, WeekBarChart, DaySelector) that the 5 screens build on, mirroring the existing `profile/ui.tsx` convention. Effort: **M** (no backend/data work, but touches all 5 screens, `AppShell`, and several e2e tests that assert on exact emoji/text).

## Context
- Stack: Next 16.2.9 (App Router), React 19.2.4, Tailwind CSS v4 via `@import "tailwindcss"` (no `tailwind.config`), TypeScript, Vitest (`tests/unit`) + Playwright (`tests/e2e`).
- Tokens today live in `src/app/globals.css`: `--background`/`--foreground` swapped under `@media (prefers-color-scheme: dark)`, mapped into Tailwind via `@theme inline`. Screens use raw `zinc-*`/`emerald-*`/`sky-*`/`amber-*`/`rose-*` utility classes directly, not semantic tokens.
- Fonts: `src/app/layout.tsx` loads `Geist` via `next/font/google` with a CSS variable (`--font-geist-sans`), wired into `@theme inline` as `--font-sans`. `globals.css` body still hardcodes `font-family: Arial, Helvetica, sans-serif` (the Geist variable isn't actually applied to `body`) — a small existing bug worth fixing while touching this file.
- There is **no icon library** in `package.json` today. All "icons" are literal emoji characters, stored as data in three places: `AppShell.tsx`'s `TABS` array, `MEAL_TYPE_ICONS`/`PANTRY_CATEGORY_ICONS` in `src/lib/types.ts`, and inline emoji in `recetas/page.tsx` (✨, ⏱️, 🔥) and `perfil/page.tsx`/`Onboarding.tsx` (🥗 title).
- All 5 target screens (`src/app/page.tsx`, `plan/page.tsx`, `recetas/page.tsx`, `despensa/page.tsx`, `perfil/page.tsx`) are single files with markup and logic inline — there's no per-screen component decomposition today except for `profile/ui.tsx` + `profile/steps.tsx`, which are **shared** between `perfil/page.tsx` and `Onboarding.tsx` (`Login.tsx` doesn't import either file — it hardcodes its own `zinc`/`emerald` classes independently, confirmed while investigating the fork decision below).
- Bottom nav lives in `AppShell.tsx` (`UserShell`), hardcoded `bg-white dark:bg-zinc-900` bar with emoji + `emerald-600` active state.
- Diario already computes everything R7 needs (`totals.calories`, `profile.calorieGoal`, the `week` array of last-7-days kcal, `maxKcal`) — R7 is a rendering change, not a data change.
- Plan already computes `dates` (7 `YYYY-MM-DD` strings via `weekDates()`) — R8 is a rendering/interaction change (add "selected day" state), not a data change.
- `tests/e2e/dashboard.spec.ts` asserts on exact visible text `"✓ 140 / 130–170"` (the protein-range-met marker, R17 from a prior spec) and `tests/e2e/recipes.spec.ts` matches a button name against `/Generar|✨/`. Both are coupled to today's exact markup/emoji and will need updating as part of this change, not as follow-up debt.
- No accessibility/contrast tooling (e.g. `axe-core`) is wired into Playwright today, so R6 (4.5:1 / 3:1 contrast) has no automated check.

## Approaches considered

### A. Semantic CSS tokens via Tailwind v4 `@theme`, dark-only, self-hosted fonts, `lucide-react` icons, new `components/ui/` layer (recommended)
Extend `globals.css` with a full set of semantic CSS variables (`--color-bg`, `--color-surface`, `--color-border`, `--color-text`, `--color-text-muted`, `--color-accent` (lime), `--color-protein` (blue), `--color-carbs` (orange), `--color-fat` (coral), `--color-expired` (red), `--color-expiring` (amber)), mapped into Tailwind utilities via `@theme inline`, the same mechanism already used for background/foreground. Drop the `prefers-color-scheme` block — `:root` *is* the dark palette. Load `Space_Grotesk` and `Manrope` via `next/font/google` in `layout.tsx` next to (or replacing) `Geist`, each with a `variable`, wired to `--font-display`/`--font-sans` in `@theme inline`. Add `lucide-react` and centralize all icon-to-meaning mappings (`MEAL_TYPE_ICONS`, `PANTRY_CATEGORY_ICONS`, nav tabs) as `Record<X, LucideIcon>` instead of `Record<X, string>`. Build a handful of shared presentational components in a new `src/components/ui/` (Card, Chip, ProgressRing, WeekBarChart, DaySelector, IconTab) that the 5 screens compose.
- **Pros**: reuses the exact pattern already in the codebase (`@theme inline` for tokens, `next/font/google` for fonts, `profile/ui.tsx` for shared primitives); tokens make future changes (including a possible future light theme) additive instead of a rewrite; `lucide-react` directly satisfies "iconos de trazo" without the SVG-maintenance cost the spec itself calls out as a risk; contrast (R6) is checkable in one place (the token values) instead of per-component.
- **Cons**: touches every screen file and `AppShell`; introduces one new runtime dependency (`lucide-react`, tree-shakeable, ~1-2 KB per icon used).
- **Effort**: M.

### B. Keep raw Tailwind utility classes, just swap the palette (zinc→new-neutral, emerald→lime) in place, no token layer
Search-and-replace `zinc-*`→ new neutral shades, `emerald-*`→ lime shades, add emoji→icon swap inline per file, no new `components/ui/`.
- **Pros**: smallest diff per file, no new abstraction to design.
- **Cons**: contrast (R6) has to be re-verified at every one of the ~40+ call sites individually with no single source of truth; doesn't fix the `body` font-family bug; five files re-implement the same card/chip/badge patterns with copy-pasted class strings, which the spec's own screens already show duplicated 5 times (`bg-white dark:bg-zinc-900 rounded-xl p-4 shadow-sm` appears verbatim in every page); makes a future light theme or icon-set swap a repeat of this same full-file-search exercise. Effort would look smaller up front but the R6 contrast risk the spec explicitly flags is much harder to close with confidence.
- **Effort**: S–M, but higher regression risk on R6.

### C. Full design-system extraction (Storybook, variant-based component library, design tokens as a versioned package)
- **Pros**: most "correct" for a growing product.
- **Cons**: this is a 5-screen, single-user personal app with no team beyond the owner; a Storybook/package split is pure overhead with no payoff here. Rejected as disproportionate.

**Recommendation: A.** It costs a bit more up front than B but directly retires two risks the spec itself names (icon-maintenance cost, lime-contrast verification) and follows conventions already present in the repo (`@theme inline`, `profile/ui.tsx`), rather than inventing new ones.

## Risks & mitigations
- **Forked profile primitives can drift out of sync.** Per Manuel's decision (see Spec feedback), `src/components/perfil/ui.tsx`/`steps.tsx` are forked copies of `src/components/profile/ui.tsx`/`steps.tsx` (which keep serving `Onboarding.tsx`) rather than shared/re-tokenized in place, so Login/Onboarding stay completely visually untouched — at the cost of two presentational copies to maintain. **Mitigation**: keep the fork strictly to the presentational layer (classnames, JSX, the new `MEAL_TYPE_ICON_COMPONENTS` map) — all business logic the two files call into (`@/lib/profileDraft`, `@/lib/nutrition`, `@/lib/allergens`, `@/lib/types`) stays shared and untouched, so a future behavior change (new field, validation rule) only has to change once; only visual/markup changes need to be applied to both copies. Add a one-line comment at the top of each forked file pointing to its sibling so a future editor notices the pair.
- **R6 contrast on lime.** Lime-on-dark and dark-text-on-lime-button are the two combinations most likely to fail 4.5:1/3:1. **Mitigation**: pick final token hex values by computing contrast ratios against the chosen background/surface before merging (a one-time manual/scripted check), not by eyeballing the prototype; there's no automated contrast check in the stack today, so this is a manual gate unless `dev-test` adds `axe-core` to Playwright as a follow-up.
- **E2e tests coupled to exact emoji/text.** `dashboard.spec.ts` (`"✓ 140 / 130–170"`) and `recipes.spec.ts` (`/Generar|✨/`) will fail the moment icons/markup change. **Mitigation**: update these as part of the same PR/task, not as follow-up debt (included in Tasks below).
- **New dependency.** `lucide-react` is a new runtime dependency; it's tree-shakeable (only imported icons ship) so bundle impact is minimal, but it's still one more package to keep patched.
- **Build-time font fetch.** `next/font/google` needs network access to Google's font files *at build time* (not at runtime — nothing is fetched in the browser). This is the same constraint the project already has for Geist today, so it's not a new risk, just worth confirming CI can reach `fonts.google.com`/`fonts.gstatic.com` during `next build`.

- Unit tests (`tests/unit/*`) are untouched — no data-layer changes; `nutrition.test.ts`, `migrate.test.ts`, `profile-draft.test.ts`, `allergens.test.ts`, `recipe-prompt.test.ts`, `recipes-route.test.ts`, `pantry.test.ts` all operate on logic that doesn't move.

- New coverage to add: active-tab highlighting in the bottom nav (R2 AC), `DaySelector` switching the displayed day in Plan (R8 AC), presence of the calorie ring + 7-bar chart in Diario (R7 AC), ingredient checklist toggling in Receta detail.
- **R6 (contrast) — done, ahead of implementation.** `axe-core` + `@axe-core/playwright` are now installed (`package.json`), and `tests/e2e/accessibility.spec.ts` runs the `color-contrast` rule against all 5 in-scope screens (plus Receta detail) with realistic seeded data. **Finding**: all 6 already fail today against the *current* zinc/emerald theme — real, pre-existing WCAG AA violations unrelated to this redesign (`text-zinc-500` on white ≈2.62:1, `text-emerald-600` on white ≈3.65:1, `text-rose-500` on white ≈3.75:1; all need ≥4.5:1). When task 12 (contrast pass) lands with the new tokens, remove the `test.fail()` calls — the suite then becomes the real, automated R6 gate the tech design originally called for a manual check for.
- `dashboard.spec.ts`/`recipes.spec.ts` matchers have already been de-risked ahead of task 13: the R17 assertion now checks the stable numeric text separately from the `✓`-in-text glyph (flagged FRÁGIL with a pointer to task 6), and the R18 button matcher now anchors on the stable "Sugerir con IA" copy instead of the `✨` emoji (the old `/Generar|✨/` pattern never actually matched "Generar" in this button — only the emoji alternative fired). ## Spec feedback
- **R10 (light theme) — recommend closing as non-goal for this iteration, not "Could".** Engineering take: maintaining two themes means every R6 contrast check (already flagged as risky for the lime accent) has to be done twice, the prototype never designed light equivalents for the lime/dark palette, and the Problem statement itself is "I want the dark, energetic, Hevy-like feel" — there's no stated user need for light mode pulling the other way. Recommendation: build the token architecture as semantic CSS variables (not hardcoded per-component colors) so a light theme is *additive* later if wanted, but don't build it now. This needs a explicit decision from Manuel since R10 is currently marked "Could — see open question," not resolved.
- **Fonts — resolved: self-host via `next/font/google`, not the prototype's Google Fonts CDN.** Same mechanism already used for Geist, zero runtime requests (fonts are fetched at build time and served from the app's own origin), no CLS, and no new privacy/dependency surface for what the spec itself calls "una app personal... sin analítica." No reason to introduce a client-side CDN dependency the app doesn't already have.
- **Perfil vs. Login/Onboarding non-goal — resolved: fork, per Manuel's decision.** This is no longer open for debate; Manuel reviewed the "accept the incidental bleed" recommendation this section previously made and decided the opposite: fork the shared profile primitives so Login/Onboarding stay **completely** visually untouched, accepting the duplication cost. Two things came out of re-checking the code against that decision:
  - **What's actually shared.** Only `Onboarding.tsx` imports `src/components/profile/ui.tsx`/`profile/steps.tsx` (for `inputCls`/`primaryBtn`/`secondaryBtn`/`chipCls` and the step components). `Login.tsx` does **not** import either file — it hardcodes its own `zinc-*`/`emerald-*` classes independently — so it was never actually at risk of visual bleed from these two files, fork or no fork. The fork therefore only needs to cover `Onboarding.tsx`'s dependency.
  - **A second, distinct bleed point in the icon maps.** `profile/steps.tsx`'s `MEAL_OPTIONS` builds its labels as `` `${MEAL_TYPE_ICONS[m]} ${m}` `` (string interpolation) and feeds `MealSlotPicker`, which both `perfil/page.tsx` and `Onboarding.tsx` render. Task 3's original plan to convert `MEAL_TYPE_ICONS` from `Record<MealType, string>` to `Record<MealType, LucideIcon>` would silently break this: you can't string-interpolate a Lucide component, and it would also change Onboarding's meal-picker icons. `PANTRY_CATEGORY_ICONS` has no such issue — it's only read by `despensa/page.tsx`, which has no Onboarding/Login path — so it converts to Lucide in place with no bleed at all.
  - **Resulting architecture**: new `src/components/perfil/ui.tsx` and `src/components/perfil/steps.tsx` (forked copies, re-tokenized, and using a new `MEAL_TYPE_ICON_COMPONENTS` Lucide map), consumed only by `perfil/page.tsx`. The originals (`src/components/profile/ui.tsx`/`steps.tsx`, plus the untouched emoji `MEAL_TYPE_ICONS`) are left exactly as-is and now serve `Onboarding.tsx` exclusively. Naming follows the existing asymmetry in the codebase between the Spanish route (`src/app/perfil/`) and the English shared-component dir (`src/components/profile/`): the new Spanish-named `src/components/perfil/` directory signals "Perfil-only, redesigned," while the existing English `profile/` directory signals "shared legacy, feeds Onboarding" — no `-v2`/`-new` suffix needed, and it reads naturally at every import site. Business logic (`@/lib/profileDraft`, `@/lib/nutrition`, `@/lib/allergens`, `@/lib/types`) is not duplicated; only the presentational layer is forked. See the Design table and Risks for detail.
